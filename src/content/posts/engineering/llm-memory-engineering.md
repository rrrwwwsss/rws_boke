## 模型其实不会自动记住你

大模型每次调用只看到本次请求携带的上下文。所谓“记忆”，是应用把过去的信息保存下来，并在合适的时候重新放进模型输入。

把全部聊天记录永远塞回 Prompt 并不是真正的记忆系统。历史越长，成本和延迟越高，旧信息还可能干扰当前任务。

一个实用方案可以分为短期、中期和长期三层。

## 短期记忆：保住当前任务

短期记忆服务于当前会话，通常包括最近几轮对话、当前目标、关键约束和刚刚得到的工具结果。

第一步是设置 Token 预算，然后按优先级裁剪：

1. 系统和安全指令不能丢。
2. 当前用户请求必须完整保留。
3. 当前任务目标和已确认约束优先。
4. 最近对话比很久以前的闲聊重要。
5. 大段、低相关的工具输出应压缩或移除。

不要简单地从字符串中间截断。这样可能留下半段 JSON、丢掉工具调用对应关系，或者只保留回答却删掉问题。

在 LangGraph 中，短期记忆通常属于 thread 的状态，并通过 checkpointer 持久化，让同一会话可以恢复。

## 中期记忆：把过程压成任务状态

对话继续增长时，可以把较早内容整理成结构化摘要。好的摘要不只是“聊了什么”，而要保存继续完成任务真正需要的信息：

```text
当前目标
已完成步骤
关键结论
用户确认的约束
工具调用结果
未解决问题
下一步动作
```

摘要后仍应保留最近几轮原始对话，因为细节、语气和临时指代很难全部压进摘要。

中期记忆还可以对旧记录做相关性召回：当前在排查数据库问题，就没有必要加载几天前的前端配色讨论。

## 长期记忆：跨会话保存稳定信息

长期记忆跨越不同会话，可以保存：

- 用户长期偏好；
- 品牌语气和格式要求；
- 已确认的业务规则；
- 产品与组织资料；
- 历史任务的最终状态；
- 经过验证的高质量案例。

长期记忆不应保存每一句聊天。先判断信息是否稳定、以后是否有用、是否允许保存，再写入持久化存储。

LangGraph 将短期记忆限定在 thread 内，而长期记忆可以按自定义 namespace 存放并跨 thread 召回。namespace 可以按用户、组织或业务对象隔离，避免不同用户的记忆混在一起。

## 记忆应该什么时候写入

有两种常见方式：

- 热路径：Agent 在回答过程中立即判断并写入。更新及时，但会增加响应延迟。
- 后台整理：先完成回答，再异步提取和合并记忆。用户等待更少，但新记忆不会立刻可用。

高风险业务还需要审核机制，避免模型把猜测或一次性的情绪写成永久事实。

## 召回不是越多越好

长期记忆的价值取决于能否在正确时机取回正确内容。可以结合关键词、向量相似度、时间、新鲜度和业务规则排序。

召回后还要检查：

- 是否属于当前用户；
- 是否已经过期；
- 是否与新信息冲突；
- 是否真的与当前问题有关；
- 是否包含不该发给模型的敏感信息。

## 一套推荐架构

```text
最近消息 + 当前任务状态
        ↓ 超过预算
结构化摘要 + 最近消息
        ↓ 需要历史信息
从长期存储检索少量相关记忆
        ↓
组装本次模型上下文
```

## 如何验证记忆系统

至少测试四类问题：

1. 记住：用户明确要求记住的信息，下次能否找回。
2. 忘记：用户要求删除后，系统是否真的不再召回。
3. 隔离：不同用户、不同项目的记忆是否串线。
4. 更新：新信息与旧信息冲突时，是否采用正确版本。

记忆系统的目标不是保存最多的信息，而是用最少、最相关、可信的信息帮助模型完成当前任务。
