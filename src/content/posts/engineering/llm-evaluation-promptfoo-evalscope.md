## 为什么不能靠手工聊天评测

随手问几个问题，只能证明模型“有时能答对”。真正的模型评测要固定测试集，同时比较基础模型、LoRA 模型、不同 Prompt 和不同推理参数，并保存每次运行结果。

一个实用评测体系至少包含两条线：

- 质量评测：答案是否正确、完整并符合格式。
- 性能评测：服务是否足够快、稳，并能承受目标并发。

Promptfoo 更适合快速组织 Prompt、模型和断言的对比；EvalScope 更适合标准能力评测及模型服务性能压测。两者可以互补，不必二选一。

## 先把测试集设计好

每条样本除了输入和期望结果，还应带上元数据：

```yaml
- question: "现场是否存在占道施工？"
  expected: "yes"
  category: "占道施工"
  difficulty: "hard"
  source: "真实误判样本"
```

元数据能让结果按类别、难度和来源分组。总准确率可能看起来提高了，但关键业务类别反而下降；没有分组就看不到这种问题。

测试集至少要分为调试集和独立验证集。反复根据同一批样本修改 Prompt，会让 Prompt 对测试集过拟合。

## Promptfoo 适合做什么

Promptfoo 可以把多个 Prompt、Provider 和测试样本排列组合，并为输出配置断言。常见断言包括：

- 精确匹配或是否包含关键词；
- 正则表达式；
- JSON Schema；
- JavaScript、Python 自定义逻辑；
- 相似度判断；
- LLM-as-a-judge。

例如结构化接口最重要的不是文字“看起来不错”，而是 JSON 能否解析、字段是否齐全、枚举值是否越界。此时 Schema 和程序断言应该优先于主观打分。

Promptfoo 还适合放进 CI：Prompt、模型版本或业务规则变化后自动跑回归测试，低于阈值就阻止发布。

## LLM 裁判不能单独使用

LLM-as-a-judge 能评价开放式回答，但裁判模型也有偏好、随机性和位置偏差。

更稳妥的做法是：能用确定规则判断的先用规则；开放问题再使用裁判模型；对关键样本保留人工盲测。还要固定裁判 Prompt、模型版本和温度，避免评测标准自己漂移。

## EvalScope 适合做什么

EvalScope 可以用于标准数据集评测，也能对兼容接口进行性能测试。性能侧常关注：

- 并发请求数；
- TTFT，首 Token 延迟；
- TPOT，每个输出 Token 的时间；
- 每秒输出 Token 数；
- 请求成功率和错误类型；
- P50、P95、P99 延迟。

平均值不能代表线上体验。少数请求等待很久时，平均延迟可能仍然漂亮，所以必须看 P95、P99 等尾延迟。

## 一套可落地的流程

1. 从真实业务中收集正确样本、边界样本和历史误判。
2. 为样本补充类别、难度、来源等元数据。
3. 使用确定性断言检查格式和明确事实。
4. 使用裁判模型评价开放式质量，并人工抽检。
5. 用 EvalScope 在固定硬件上测延迟、吞吐和稳定性。
6. 保存配置、模型版本、提交号和原始结果。
7. 新版本与当前生产基线比较，不只与“空白模型”比较。

## 最终该看哪张表

| 维度 | 最低要求 |
|---|---|
| 任务质量 | 总体指标和关键类别指标不下降 |
| 输出格式 | Schema、字段和类型全部通过 |
| 性能 | TTFT、TPOT、吞吐满足业务目标 |
| 稳定性 | 错误率和 P99 延迟在阈值内 |
| 成本 | 单请求或每百万 Token 成本可接受 |

评测不是为了找一个“最高分模型”，而是确认新版本在质量、速度、稳定性和成本之间达到了可上线的平衡。
