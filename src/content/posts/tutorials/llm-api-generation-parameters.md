## 先从一套稳妥配置开始

```json
{
  "temperature": 0.2,
  "top_p": 0.9,
  "max_tokens": 1024,
  "repetition_penalty": 1.05
}
```

这套配置适合报告生成、信息提取和问答等偏稳定的任务。不同模型对参数的支持和解释可能略有差异，使用前应查看具体服务接口。

## temperature：回答有多敢选小概率词

Temperature 会调整下一个 Token 的概率分布。

- 较低：答案更稳定、更集中。
- 较高：答案更多样，也更容易跑偏。

事实问答、分类和结构化抽取可以从 `0` 到 `0.3` 开始；写作和头脑风暴可以从 `0.7` 左右开始。低温不等于绝对可复现，推理后端和并行计算仍可能带来差异。

## top p：只在主要候选中选择

`top_p: 0.9` 表示按概率从高到低选择候选，直到累计概率达到约 0.9，再从这批候选中采样。

它根据每一步的概率分布动态改变候选数量。模型很确定时，候选较少；模型不确定时，候选较多。

Temperature 和 top_p 都会控制随机性。初次调参时建议固定一个，只重点调整另一个，避免不知道变化由谁造成。

## top k：最多保留多少个候选

`top_k: 20` 表示每一步最多考虑概率最高的 20 个 Token。它的候选数量固定，和 top_p 的累计概率机制不同。

并非所有 OpenAI 兼容接口都公开支持 top_k。接口不支持时不要自行假设参数已经生效，要检查服务端日志或返回错误。

## repetition penalty：减少机械重复

重复惩罚会降低已经出现过的 Token 再次被选择的机会。`1.0` 通常表示不额外惩罚，大于 1 会增强惩罚。

数值过高可能破坏必要重复，例如代码变量、法律条款名称和固定 JSON 字段。它更适合修复确实存在的循环复读，不应作为所有任务的默认“质量增强器”。

## max tokens：限制本次最多生成多少

`max_tokens` 或部分接口中的 `max_completion_tokens` 限制输出长度，不是输入加输出的总长度。

实际请求仍受模型最大上下文约束：

```text
输入 Token + 可生成 Token <= 模型与服务允许的上下文长度
```

设置过大会占用调度预算，设置过小则可能让回答被硬截断。结构化输出被截断后经常变成不完整 JSON，因此必须结合业务长度设置。

## 三套起步配置

| 场景 | temperature | top_p | 建议 |
|---|---:|---:|---|
| 分类、抽取、执法判断 | 0～0.2 | 0.9～1.0 | 优先稳定和格式正确 |
| 通用问答、报告生成 | 0.2～0.5 | 0.9 | 保留少量表达变化 |
| 创意写作、方案发散 | 0.7～1.0 | 0.9～0.95 | 接受更高随机性 |

这些只是起点，不是最佳答案。模型、Prompt 和数据一变，合适参数也会变化。

## 正确的调参方法

1. 固定模型版本和测试集。
2. 确定质量、格式、延迟和成本指标。
3. 一次只调整一个主要参数。
4. 每套配置运行多次，观察稳定性。
5. 按简单、困难和历史误判样本分组比较。
6. 把最终参数保存在版本控制中。

不要用“感觉这次回答不错”做结论。推理参数应该和 Prompt、模型版本一起接受回归测试。
